ChainDraw — Validation Sprint

Trustless social giveaways on Solana · devnet MVP live at luckydraw.y09.space · validated 2026-08-15 via /validate-idea

Verdict: PIVOT (channel), keep the rails — confidence 0.6

The trust problem is real and well-evidenced, the build is proven (MVP already live), and crypto is genuinely load-bearing for the verifiability story. But the Mastodon-first wedge fails the demand test: fediverse culture is explicitly hostile to brand promotion and largely hostile to crypto, and zero organizer-side demand signals were found. Same codebase, swap the social adapter: Farcaster first (crypto-native, open API, users already have wallets), Bluesky second. Do not build further features until 5 organizer conversations confirm pull.

Demand signals found

  • The problem is real and large: giveaway scams tracked at ~$98M profit in 2021 (Whale Alert); security vendors publish recurring Solana-giveaway-scam advisories; "99.9% of crypto giveaways on Twitter are scams" is a common refrain in coverage.
  • Winner-selection disputes are a known pain: how-to content exists specifically on picking crypto giveaway winners "without disputes" — evidence organizers worry about being accused of rigging.
  • Multiple funded/live teams in adjacent raffle space (GiveFi, raffl via Colosseum, SolPrize) — the "provably fair draw" concept has independent convergent interest on Solana.
  • Missing: any Mastodon/fediverse organizer asking for giveaway tooling; any brand running Solana-prize campaigns on Mastodon; any entrant complaining they can't verify a fediverse giveaway. Searched — found nothing.

Integration-first assessment

The remaining roadmap is mostly integration, not novel program development — an advantage (faster ship, lower audit surface):

  • Verifiable randomness: integrate Switchboard On-Demand VRF or ORAO VRF instead of the server seed — no custom program needed.
  • Escrow: the only place a small custom Anchor program (or an existing token-escrow primitive) is justified; scope it to lock-at-commit / release-to-winners. The schema already reserves delegation_pda.
  • Payouts: plain SPL transfers; no protocol needed.
  • Social adapters: Farcaster (Neynar API / hub) and Bluesky (AT Protocol) both expose likes/reposts/follows — the mastodon.server.ts pattern ports directly.

Next steps (2-week validation sprint — before writing more code)

  • 1. Organizer interviews (days 1–7): talk to 5–10 people who run giveaways today — Solana NFT/memecoin community managers, Farcaster channel owners, indie creators. Ask "how did you run your last giveaway, and what was the most annoying part?" — not "would you use this?"
  • 2. Run one real giveaway (days 3–10): use ChainDraw yourself for a small devnet-prize campaign in a crypto-friendly community; measure the funnel (viewed → signed in → verified → entered) and collect entrant reactions. Dogfooding is the fastest honest signal.
  • 3. Channel pivot spike (days 7–12): prototype a Farcaster verification adapter (Neynar API) behind the existing interface; Farcaster users are crypto-native and hold wallets — the culture fit Mastodon lacks.
  • 4. Tighten the trustless claim: until escrow ships, label commitments honestly ("public commitment", not "no trust required") — or fast-follow with the escrow program + VRF integration if organizer interviews confirm pull.
  • 5. Draft official rules template (sweepstakes compliance: no-purchase language, eligibility, void-where-prohibited) — cheap insurance, and itself a selling point for organizers.
  • Decision gate: ≥3 organizers say they'd run their next giveaway on it → persist and build escrow/VRF. Zero pull after 10 conversations → shelve or pivot the layer (sell verification-as-API to existing raffle platforms).
